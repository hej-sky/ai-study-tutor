## 0. 一条原则：只改仓库

内容只改 Gitee 仓库，仓库外不再保留第二份发布工作区。`release/` 里所有物料都从仓库文档派生，**不要解压后手改 ZIP 里的文件**。

构建入口按产物分两个，都不另存内容副本：

| 脚本 | 产物 | 说明 |
|---|---|---|
| `build_release.py` | 技能包 `ai-study-tutor-v1.7.0.zip` | 从仓库文档派生，含 frontmatter、精简版使用说明 |
| `build_expert.py` | 专家包 `ai-study-tutor-expert-v1.7.0.zip` | 直接读上面那个 ZIP 与头像组装，**技能部分逐字节同源** |

原因：每个平台更新都要重传重审，WorkBuddy 还有提交次数限制；手改两份必然分叉。

## 5. 渠道 ②-B 开放平台「专家」

**先看这段再决定要不要发**：「专家」和「技能」是两类不同资产，解析器不同，同一个 ZIP 不能混用。

| 项 | 技能入口 | 专家入口 |
|---|---|---|
| 解析器找的文件 | 压缩包根层 `SKILL.md` | `.codebuddy-plugin/plugin.json` |
| 包结构 | 根目录 / 二级目录，最多两层 | 顶层目录 + `agents/` `avatars/` `skills/` `README.md` |
| 本质 | 一份 Skill 定义 | Agent 角色包（人设 + 挂载 Skill 当能力） |
| 市场位置 | 「专家·技能·连接器 → 技能」 | 「专家·技能·连接器 → 专家」 |

**入口别混**：技能包传进专家入口会报「未找到 .codebuddy-plugin/plugin.json」，专家包传进技能入口会报「未找到 SKILL.md」。两种报错都是入口选错，不是文件损坏，换包或换入口即可——不要给技能包补一个 `plugin.json` 硬凑。

### 上传步骤

1. 「发布管理 → **专家** → 创建」上传 `ai-study-tutor-expert-v1.7.0.zip`（只传这一个 ZIP，不要传整个 `release/` 目录）。
2. 若仍提示「未找到 .codebuddy-plugin/plugin.json」，改传备用包。备用包不随仓库分发，用到时再生成：

   ```bash
   python release/build_expert.py --flat
   ```

   它和主包内容完全一致，差别只在是否套一层顶层目录：主包对标官方模板（带顶层目录），备用包按「解析文件须在压缩包根层」的经验拍平。
3. 解析通过后确认展示信息：分类选「教育学习」，头像用 `avatar-512.png`，免费，提交审核后仍需手动点「发布」。

### 包内口径（定义在 `build_expert.py`，别处不再写一份）

- `expertType: "agent"`（单角色，非专家团）；`categoryId: "15-Education"`。
- `displayDescription.zh` 由脚本校验在平台要求的 40~50 字区间；`tags` / `quickPrompts` 各 3 条，`defaultInitPrompt` 与第一条 `quickPrompts` 相同，三条提示词沿用技能包 frontmatter 的 `examples`。
- Agent 定义文件不复述完整提示词，只声明「加载随包 Skill 并读取 `system-prompt.md` 作为唯一权威规则」，避免两份口径分叉。
- `author.email` 取自仓库 git 提交作者邮箱，会随包公开；不愿公开就改 `build_expert.py` 里 `PLUGIN_JSON` 这一处。
- 头像是扁平图标，不是人物插画。若审核要求人物插画，再单独生成替换。

### 本地校验

```bash
python release/build_expert.py
```

预检覆盖平台字段规范（双语、40~50 字、tags 数量、路径可解析、无 `tools` 声明、头像规格）与打包卫生（无 `__MACOSX` / `.DS_Store` / 本机路径 / 凭据 / TODO 残留）。

## 7. 升版本流程

1. 改仓库 → 跑 `python check_repo.py` → commit / push（**master 与 develop 都要推**，Gitee 默认分支是 master）。
2. 改两个脚本里的 `VERSION` → 先跑 `build_release.py`，再跑 `build_expert.py`（版本不一致时后者找不到技能包会直接报错）。
3. 删掉旧版本 ZIP，把新 ZIP 一起提交；打新 tag 并推送。
4. Gitee Release 换新 ZIP；WorkBuddy 后台点「更新版本」重传并**重新审核**（会重置头像，记得重传）。
5. 所有渠道版本号保持一致。

### 7-1. 版本号只给维护者看（发版必查）

版本号是**维护侧的可追溯编号**，用来关联 tag、构建产物、评测基线和双端核对，不是给使用者看的产品等级。使用者看到 `v1.7.0` 会有两种误读：一是「我是不是装旧了」——但平台存的是上传快照、客户端也不显示版本，他根本无从查证也没有行动路径；二是把「迭代了七次」读成成熟，反而盖住真实状态（零真人验收）。顺带还有个一词两义：项目里「版本」也指**教材版本**（人教版 / 北师大版），清掉软件版本号正好消歧。

| 层 | 范围 | 要求 |
| --- | --- | --- |
| 机器层 | tag、ZIP 文件名、`plugin.json` 的 `version`、上架包 `SKILL.md` frontmatter 注入的 `version`、两个构建脚本 `VERSION` | **一字不动**，删了发布工程、客户端更新判断与评测基线会崩 |
| 维护层 | `CHANGELOG.md`、本清单、`eval-checklist.md`、`开发修改记录.md` | **完整保留**，这才是版本号真正的主场 |
| 使用者层 | `README.md`、`usage-guide.md`、上架包内三个文件的正文 | **不出现软件版本号** |

**唯一例外**：`真人试用说明.md` 必须写清「测这份 v1.7.0，别测技能库里的 v1.6.0」——测试者要靠它区分两份不同内容，版本号在这里是**消歧工具**，不是状态展示。所以原则是「版本号只在需要消歧时出现」，不是「一律不许出现」。

**替代物**：`最近更新：2026-11-11` 代替版本号（日期表达新旧、不带成熟度暗示）；用行为描述（「AI 会先给思路提示，不直接给答案」）代替「这一版新增了什么」；状态说明保留「还在打磨、正在收集真实反馈」。下载链接的**文字**写「下载技能包（ZIP）」，带版本号的文件名留在链接地址里——那是附件名与哈希校验所需，不是产品等级。

## 8. 避坑清单

- **ZIP 结构**：技能包解压第一层必须是 `SKILL.md`；专家包必须含 `.codebuddy-plugin/plugin.json`。两个脚本各自校验，别拿错 ZIP。
- **YAML**：两个空格缩进、冒号后有空格、不用 Tab、不加引号；`name` 只用英文小写加连字符且与目录名一致。脚本已校验。
- **提交次数**：WorkBuddy 每天技能 / 专家各 5 次、每月合计 20 次，驳回重提也算。先在本地跑自检再传，别反复试错。
- **名称**：含别家平台名会被驳回；展示名别带「测试」「最终版」。
- **头像**：512×512、JPG/PNG、≤500 KB；「更新版本」会重置头像。
- **过审 ≠ 上线**：必须手动点发布并选「公开发布」。
- **免费 / 付费不可改**：默认免费，别误点。
- **未成年人教育内容**：`description` 不要写「保证提分」之类的效果承诺；隐私与免责沿用 README 的「许可与免责」。
- **死链**：派生文档里指向仓库本地文件的链接都已改成线上地址，脚本会逐处扫描（数量随内容变化，不写死）；改完内容记得重跑自检。
- **能力边界口径**：以 `usage-guide.md` 末尾「附：客观能力边界」为唯一权威，本清单不另写一套。
